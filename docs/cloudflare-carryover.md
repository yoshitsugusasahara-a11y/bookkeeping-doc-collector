# Cloudflare側へ引き継ぐ判断と教訓

現行環境（Vercel + Supabase）で決めたことのうち、**Cloudflare版を作るときに知らないと同じ失敗を繰り返すもの**を記録する。

## このファイルが必要な理由

Cloudflare側へ渡すものは2種類あり、**片方はgitでは追えない。**

| 種類 | 中身 | 伝え方 |
|---|---|---|
| ① コードの変更 | 持ち込み対象ファイルの修正 | **gitの範囲指定**で機械的に出る（下記） |
| ② **判断と教訓** | **作り直す領域**に入れた設計判断・踏んだ罠 | **このファイル** |

②が問題になる。画面と処理フローはCloudflare側で作り直すため、**コードを写さない。**
写さないということは、そこに込めた判断も一緒に消えるということで、**伝えなければ同じバグを作り直す。**

実例: 2026-09-10の修正2件は `app/client/.../submissions/page.tsx`、`app/admin/.../page.tsx`、
`lib/receipts/process-submissions.ts` の3ファイルだけを変更した。**3つとも持ち込み対象外**なので、
gitの範囲指定では**何も出てこない。** しかし内容は新環境でもそのまま当てはまる。

### ①のやり方（コードの変更）

Cloudflare側が「どの時点のコードを写したか」を記録しておけば、差分は機械的に出せる。

```
git log <写した時点のsha>..main -- lib/gemini lib/moneyforward lib/receipts/send-mode.ts lib/receipts/submission-filters.ts lib/images/shrink-image.ts docs
```

持ち込み対象:

- `lib/gemini/` — OCR・分類・仕訳生成のプロンプト
- `lib/moneyforward/` — APIクライアント・予測仕訳・事業者情報・エラー文言の分類・会計年度
- `lib/receipts/send-mode.ts`
- **`lib/receipts/submission-filters.ts`** — 2026-09-10に追加。小さいが**SQLの三値論理の罠**がコメントに書いてある（下記の教訓6）
- `lib/images/shrink-image.ts`
- `docs/`

`lib/receipts/process-submissions.ts` は**含まない。** OCRの処理フローはQueues前提で作り直すため。
つまり**このファイルに入れた判断は、すべてこの引き継ぎ文書の担当になる。**

### 書き方

**その場で書く。** あとでまとめて思い出そうとすると必ず漏れる。1件3行でよい。

### 渡す時期

定期的に渡すほか、**節目で必ず渡す。**

1. **フェーズ4（設計）の前** ← ここが一番効く。実装後に伝えると作り直しになる
2. 実装開始の前
3. リリース前

## 教訓

### 1. レシート以外の資料をMFへ送らない（2026-09-09 / `d238ce5` `a73fce4`）

**何を:** 資料分類で「レシート以外」と判定されたものは、送信処理の入口で拒否する。
Cronと管理者の一括処理の対象抽出からも除く。顧客画面の送信ボタンも押せなくする。

**なぜ:** 判定はしていたのに、**送信側が判定を見ていなかった。** レシート以外の資料に仕訳が作られ、
MFへ送られた。「分類する」と「送信する」が別の処理で、後者が前者の結果を参照していなかった。

**新環境で:** 分類結果を見るのは1箇所では足りない。**送信の入口・対象抽出・画面のボタンの3箇所**で
それぞれ弾く。どれか1つでも欠けると経路が残る（実際、入口だけ塞いだ時点ではCronから漏れていた）。

### 2. 判定をやり直せるよう、元ファイルを残す（2026-09-09 / `a73fce4` `a40fff5`）

**何を:** レシート以外と判定した資料でも、一時保存した元ファイルを消さない。
「読み取り直す」はOCRだけでなく**分類からやり直す。** 判定が変わったらDrive上のファイルも移動する。

**なぜ:** 判定を誤ったときに直す手段が無かった。元ファイルを消していたので、やり直しようがなかった。

**新環境で:** 自動判定には必ず**人がやり直せる経路**を用意する。やり直しに必要な入力（元ファイル）を
捨てない。判定を変えたら、判定に紐づく副作用（保存先）も追従させる。

### 3. 外部リソースのIDは、保存する前に実在を確かめる（2026-09-09 / `54db13b`）

**何を:** 分類ルールに登録するDriveフォルダIDを、保存時に検証する（実在・種別・書き込み権限）。
顧客単位のフォルダには既に入れていた検証を、ルール側にも広げた。

**なぜ:** 存在しないフォルダIDが登録でき、**資料の分類時に初めて失敗した。** しかも失敗の仕方が悪く、
例外で巻き戻って分類結果ごと消え、画面には何の説明も出ず、資料が「OCR待ち」のまま宙に浮いた。

**新環境で:** 2点。**(a)** 外部リソースのIDは入力時に検証する。**(b)** 外部への保存が失敗しても、
**そこまでに確定した判断は記録する。** 例外で全部巻き戻すと、原因が画面にもログにも残らない。
フォルダは後から削除・移動されうるので、これは想定すべきケースであって異常系ではない。

### 4. 仕訳を登録する会計年度を明示的に決める（2026-09-09 / `3f0c609` `f07917b`）

**何を:** 送信先の会計年度を設定できるようにし、取引日がその範囲外なら送信しない。
選択肢はMFから取得した会計期間のみ（自由入力させない）。

**なぜ:** **MFは取引日がいずれかの会計期間に入っていれば受け付ける。** 過去年度が残っている事業者では、
日付を読み違えた資料が過去年度へ**静かに**登録される。実際に発生し、仕訳を手作業で削除した。
「全期間の外」だけはMFが弾くが、それは裏を返せば**過去年度がある限り弾かれない**ということ。

**新環境で:** 外部APIが「受け付ける」ことと「正しい」ことは別。**受け入れ範囲が広いAPIほど、
こちら側で絞る必要がある。**

**「自動」の定義は「最新の会計期間」。2026-09-10にユーザーが明示的に選んだ仕様。**
「今日を含む期間」への変更を提案したが、不要と判断された（東京商会はテスト用で実ユーザーがおらず、
手元のレシートが古いため意図的にこの状態にしてある）。**蒸し返さないこと。**
既知の限界として、MF側の会計期間が現在に追いついていない事業者では、直近の締まった年度へ
古い日付の資料が入りうる。

### 5. 編集操作が、他の処理の置いた状態を巻き戻さないようにする（2026-09-10 / `626e932` `42c523b`）

**何を:** OCRの手入力フォームを出す条件を絞った。

| 状態 | フォーム |
|---|---|
| レシート以外と判定 | **出さない**（「読み取り直す」へ誘導） |
| 読み取り中（pending） | **出さない**（「読み取り中です」と表示） |
| 解析済み（completed） | 出す |
| **失敗（failed）** | **出す** — 手入力が唯一の復旧手段。ここを塞ぐと詰む |

**なぜ:** OCR保存の処理は `ocr_status` を `completed`、`mf_status` を `not_sent` に戻し、
予測仕訳を破棄して作り直させる。これは**レシートを前提にした正しい動作**だが、他の状態から呼ぶと壊れる。

- **レシート以外の資料で保存すると**、判定に基づいて置いた `skipped` / `not_ready` が巻き戻り、
  「レシート以外なので仕訳は作りません」の説明が消え、**請求書に対する仕訳が作られる**（Geminiを1回消費）
- **読み取り中に保存すると**、10〜20秒後に完了した背景処理が**手入力を上書きして消す。**
  保存は成功したように見えるので気づけない

**新環境で:** これは画面の話ではなく**状態遷移の話。** 「編集」「再実行」のような操作は、
他の処理が置いた状態を無条件に上書きしがち。**操作を許す条件を状態ごとに決める。**
そして**画面で塞ぐだけでは足りない** — 予測仕訳を拾う側にも同じ条件を入れた。
判定が後から変わった資料や、既に別の状態で残っている過去データが漏れるため。

### 6. SQLの三値論理でnullが落ちる（`lib/receipts/submission-filters.ts` のコメント）

**何を:** 「レシート以外」を除く条件を `.neq("document_kind", ...)` で書かない。
`document_kind is null or document_kind = 'receipt'` と明示する。

**なぜ:** `neq` で書くと、**分類がまだ終わっていない資料（null）が三値論理で除外され**、
どちらの絞り込みにも現れなくなる。分類前の資料は「レシートかどうか未確定」として残す必要がある。

**新環境で: D1もSQLiteなので同じ罠がある。** このファイルは持ち込み対象に入れてある。

### 7. 背景処理には「処理中」の印が要る（2026-09-02 / `f81db41`、2026-08-06 / `a17604a`）

**何を:** OCRを始める前に、条件付きUPDATEで資料を「取る」。他が先に取っていたら次の候補へ移る。
印は3分で期限切れにして、中断された資料が取り残されないようにする。

**なぜ:** 一括アップロードすると、**ファイルごとに背景処理が起動して全員が同じ最古の1件を掴み**、
残りには誰も手を付けなかった。`ocr_status` は解析が終わるまで `pending` のままで、
排他制御が無かった。本番顧客の環境で数十枚が滞留した。

**新環境で: Queuesを使うので、この問題は構造的に起きない**（1レシート＝1メッセージ、
可視性タイムアウトが処理中ロックそのもの）。**Queuesを採用する理由がこれ。**
ただし「Queuesを使わない箇所」を作るなら、同じ罠が待っている。
